# Field Force — Super admin: onboard promoter & salesman

Guide for **Abhiroop / super admin**: how to register promoters and salesmen today, what the **tenant selector** means, and whether they can self-register.

**Do not use raw SQL for login accounts** — passwords are hashed in auth-service. Use **UI** or **`scripts/setup-fieldforce-login.ps1`**.

---

## What you see on screen

### `/admin/field-force`

| Part | Purpose |
|------|---------|
| **Tenant dropdown** | Field force data is **per tenant**. Pick tenant (e.g. Tenant 1, 101) before promoters/salesmen load. |
| **Promoters table** | People rows in `fieldforcedb.promoters` (code `PF-6`, etc.) — **profile only, no login yet** |
| **Salesmen table** | Rows in `fieldforcedb.salesmen` (code `SF-5`) linked to a promoter |
| **Commission plans / entries** | Payout rules (optional setup) |

Adding a promoter here **does not create login**. They cannot sign in until step 3 below.

### `/admin/create-login-invite`

Creates **auth login** linked to field-force id (`promoterId` or `salesmanId`).

---

## Recommended flow (3 steps)

### Step 1 — Pick tenant & create promoter

1. Go to **`/admin/field-force`**
2. Select **Tenant** (must match the tenant’s shops, e.g. tenant `101` if shops use tenant 101)
3. **Add promoter** → fill form (see your screenshot: Anand Mishra, mobile, state/city, joining date)
4. **Save promoter** → note **ID** and code (**PF-6** means `promoters.id = 6`)

### Step 2 — Create salesman (under that promoter)

1. Same page, **Add salesman**
2. Select **Promoter** (e.g. PF-6 — Anand Mishra)
3. Fill name, mobile, state, city, joining date
4. **Save salesman** → note **ID** and code (**SF-5** → `salesmen.id = 5`)

### Step 3 — Login invite (creates username + password link)

1. Go to **`/admin/create-login-invite`**
2. Fill:

| Field | Promoter example | Salesman example |
|-------|------------------|------------------|
| **Shop ID** | Any **ACTIVE** shop in that tenant (anchor), e.g. `GEN-DEMO-01` | Same — e.g. `GEN-DEMO-01` |
| **Tenant ID** | Same as field-force tenant, e.g. `101` | Same |
| **Username** | Short id, e.g. `anand` | e.g. `raju` |
| **Email** | Real email for set-password link | Real email |
| **Role** | **Field force — promoter** | **Field force — salesman** |
| **Promoter ID / Salesman ID** | `6` (from step 1) | `5` (from step 2) — **required** |

3. Click **Create invite**
4. Copy **`/onboarding/set-password?token=...`** link → send to promoter/salesman (or email if configured)
5. They set password once

### Step 4 — Tell them how to login daily

| Field | Value |
|-------|--------|
| URL | `/login` |
| Mode | **Employee** |
| Shop ID | Same as invite (e.g. `GEN-DEMO-01`) |
| Username | Base username (e.g. `raju`) |
| Password | What they set |

→ Lands on **`/field-force/workspace`**

## Easiest path: one PowerShell script (local/dev)

Automates steps 1–3 + prints login card:

```powershell
cd d:\sugamFlow

# New promoter + login
.\scripts\setup-fieldforce-login.ps1 -Role PROMOTER `
  -TenantId 101 -ShopId GEN-DEMO-01 `
  -Username anand -Password 'Anand@2026' `
  -PromoterName 'Anand Mishra' -Mobile 9899758514

# New salesman under existing promoter id 6
.\scripts\setup-fieldforce-login.ps1 -Role SALESMAN `
  -TenantId 101 -ShopId GEN-DEMO-01 `
  -Username raju -Password 'Raju@2026' `
  -SkipPromoterCreate -ExistingPromoterId 6 `
  -SalesmanName 'Raju' -Mobile 9711675041
```

Requires: gateway :9090, auth-service, fieldforce-service, and shop row `GEN-DEMO-01` exists for tenant 101.

## Fix broken logins (your auth_account screenshot)

Some rows have **`salesman_id = NULL`** — those accounts **cannot** use Field Force workspace.

```sql
-- authdb
SELECT shop_id, username, role, salesman_id, tenant_id, promoter_id
FROM auth_account
WHERE role IN ('FIELD_FORCE_SALESMAN', 'FIELD_FORCE_PROMOTER');
```

**Fix:** Re-create invite with correct **salesman id** / **promoter id**, or update row only if you know the correct ids:

```sql
UPDATE auth_account SET salesman_id = 5
WHERE username LIKE '%raju%' AND role = 'FIELD_FORCE_SALESMAN' AND shop_id = 'GEN-DEMO-01';
```

Prefer **Admin → Login invite** reissue over manual SQL when possible.

## Why NOT plain INSERT scripts?

| Table | Manual SQL? | Why |
|-------|-------------|-----|
| `fieldforcedb.promoters` / `salesmen` | Possible but awkward | Codes are `PF-{id}` / `SF-{id}` after insert; use UI/API instead |
| `authdb.auth_account` | **Avoid** | Password must be BCrypt hash; use **Create invite** + set-password flow |
| `authdb` invite token | **Avoid** | Generated by auth-service |

**Reference only** — promoter row via API is better. If you must inspect after UI save:

```sql
-- fieldforcedb (user fieldforcedb)
SELECT id, promoter_code, full_name, mobile, tenant_id, status FROM promoters;
SELECT id, salesman_code, promoter_id, full_name, mobile, tenant_id FROM salesmen;
```

## Can promoter/salesman register themselves?

### Today: **No full self-registration**

Public **`/register`** is for **shop owners**, not field force. There is no “Sign up as promoter” page.

### What is already “self-serve”

| Step | Who |
|------|-----|
| Set password from invite link | Promoter/salesman (self) |
| Daily login + leads + demo | Promoter/salesman (self) |
| Create profile + invite | **Super admin only** |

### Suggested operating model (easiest now)

```
Super admin (2 min)          Field person (self)
─────────────────           ───────────────────
Create promoter/salesman    Open invite link
Create login invite    →    Set own password
Send link/email             Login anytime (Employee + shop id)
```

Admin does **identity + tenant** once; person owns **password + daily field work**.

### Future improvement (if you want more self-serve)

| Option | Effort | Notes |
|--------|--------|-------|
| **A — Invite-only (current)** | Done | Best for control & KYC |
| **B — “Apply as promoter” form** | Medium | Public form → `PENDING` row → admin approves → auto invite email |
| **C — Promoter invites salesman** | Medium | Logged-in promoter adds salesman + triggers invite (no super admin) |
| **D — Full open signup** | Not recommended | No tenant control, duplicate/fake accounts |

**Recommendation:** Keep **A** for production; add **C** next so Anand (PF-6) can onboard Raju without Abhiroop every time.

## Tenant + Shop ID cheat sheet

| Concept | Example | Used for |
|---------|---------|----------|
| **Tenant ID** | `101` | All field-force rows scoped to tenant |
| **Shop ID (login anchor)** | `GEN-DEMO-01` | Auth login only — **not** the shop they visit in field |
| **Promoter code** | `PF-6` | Display; login uses numeric **id = 6** in invite |
| **Salesman code** | `SF-5` | Display; login uses **id = 5** in invite |

Tenant in **Field force admin** must match **Tenant ID** on **Login invite**.

## Quick checklist (super admin)

```
□ Tenant selected on /admin/field-force
□ Promoter created → note id (PF-x)
□ Salesman created under promoter → note id (SF-x)
□ Shop exists for tenant (e.g. GEN-DEMO-01) — ACTIVE or at least exists for auth
□ Login invite: role + promoterId/salesmanId filled
□ Person received set-password link and completed it
□ Verify auth_account.salesman_id / promoter_id NOT NULL
□ Person can login: Employee + shop id + username
```
